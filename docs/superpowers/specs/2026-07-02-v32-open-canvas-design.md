# v32 — Open Canvas (design spec)

**Status:** draft, awaiting user review.
**Date:** 2026-07-02.
**Model note:** v32 is the first SnapShotPro version directed under GLM-5.2 (the model driving the brainstorm/plan/build session). Recorded here and later in the changelog / What's-New toast.

## 1. One-sentence summary

Open Canvas turns the studio into an **infinite canvas you seed from a URL and sculpt by conversation**: a freeform 2D board of full design scenes, populated by pasting a link, and driven by a conversational AI agent.

Three pillars, one release:

- **Space** — an infinite canvas (the Board): a pan/zoom surface of cards, text, arrows, and groups.
- **Seed** — URL to set: paste a page URL, get on-brand board cards auto-dropped and arranged.
- **Control** — Conversational studio: the AI agent becomes the primary interface for board-level intent.

This is a paradigm-shift release (the largest since v21's 3D mockups), built as **thin orchestration over engines that already exist** — the v30/v31 flagship shape.

## 2. The key realization (and the load-bearing reuse)

The studio already has a full-scene, id-keyed, persisted multi-page engine: **`src/features/pages.js`** (v13, Multi-Page Canvas and Deck Mode).

- `pages = [{ id, payload, thumb }]`. Each `payload` is a complete `serializeFull()` design envelope (all `PROJECT_FIELDS` plus image dataURL). Pages are id-keyed and persist via projects.js (`serializeDocument` / `applyDocument`).
- `switchTo(i)` serializes the live page, `applyPayload(target)`, re-renders. This is the "double-click a board card to open it in the editor" path. It already exists.
- `renderAllPages()` does `applyDesignToState(payload)` then `renderInto(off, true)` per page. This is the board export path. It already exists (deck PDF/ZIP/present use it).
- `makeThumb()` / `page.thumb` are the card previews. They already exist (the filmstrip renders them).

So a **board card is a page**. The board is a spatial, editable, conversational layer *over* `pages.js`, not a new multi-scene renderer. `renderInto` and the four composition paths do not change. `screenshot-set.js` stays untouched doing its store-sized-set job.

## 3. Architecture

### 3.1 State

New document-level state, kept on `state` for convenient access but **not** snapshotted by `history.snapshot()` (mirroring how `state.canvasSelection` is on-state but runtime-only):

```js
state.board = {
  objects: [   // spatial layout, document-level (one layout for all pages)
    { id, kind, x, y, w, h, z, rotation?,
      pageId?,          // kind === 'card' -> a pages[i].id (the scene payload lives there)
      text?, fontSize?, color?, align?,  // kind === 'text'
      from?, to?,       // kind === 'arrow' -> object ids it connects
      children?         // kind === 'group' -> object ids
    }
  ],
  camera: { x, y, zoom }   // runtime-only pan/zoom; not snapshotted, not serialized
}
state.boardSelection = []  // runtime-only, parallel to canvasSelection; array of refs {kind:'boardObject', id}
```

Kinds: `card` (refs a page by id), `text`, `arrow`, `group`.

Why `state.board` is document-level, not per-design: the board is the *container* of all pages; there is one layout for the whole document, exactly like `active` is document-level metadata about which page is live. It cannot live per-page.

### 3.2 Render strategy (honest, hybrid)

- **Board surface = a DOM layer.** A camera-transformed container holds absolutely-positioned card nodes + an SVG overlay for arrows/connectors + text nodes. DOM is the right tool for freeform pan/zoom/selection and avoids a giant live multi-scene canvas.
- **Each card shows the existing `page.thumb`** as its cached raster preview, regenerated by the existing `makeThumb()` / `syncActive()` machinery (debounced `onHistoryChange` already refreshes the filmstrip; the board subscribes the same way).
- **`render.js` gets one branch**, mirroring the existing `state.mode === 'set'` early-return:

  ```js
  if (!forExport && state.mode === 'board') { renderBoard(); return; }
  ```

  `renderBoard()` lays out the DOM board from `state.board` (cards positioned by `{x,y,w,h,z}`) and draws selection chrome. It does **not** run the canvas passes for its own chrome; per-card scene pixels come from the cached thumbs (preview) or `renderAtSize` per card (export).
- **Double-click a card** = resolve the card's stable `pageId` to an index (`pages.findIndex(p => p.id === pageId)`), then `switchTo(index)` (existing). Entering a card flips `state.mode` from `'board'` to `'single'` (the normal scene editor); returning to the board flips it back. The unchanged editor opens over the board; the user edits the scene normally; switching back calls `syncActive()`, refreshing that card's thumb. Zero edits to `renderInto`.
- **Two views, one document.** The existing page filmstrip and the board are two views of the same `pages` array. Adding, deleting, or reordering pages in either view is reflected in the other; the board only adds spatial coordinates, connectors, and grouping on top of the page list.
- **Board export** composites: for each card, `applyDesignToState(pages[i].payload)` + `renderInto(off, true)` (the existing `renderAllPages` loop), then `drawImage` each offscreen result at the card's board rect onto one board canvas, then draw the SVG connectors/text overlays. This is the same "render offscreen at the end, then composite" idea `tour-export.js` already uses.

### 3.3 Selection

`src/features/selection.js` is **unchanged** for scene objects. A parallel, board-space selection is added:

- `state.boardSelection` (runtime-only, array of `{kind:'boardObject', id}`).
- A `resolveBoardRef(ref)` returns the same uniform handle shape (`box`, `moveBy`, `clone`, `remove`, `raiseToFront`, `sendToBack`) operating in **board pixels** (no fractional/canvas conversion, since board objects store absolute board px). The *interface* ports from `resolveRef`; the *coordinate space* differs, so it is a separate resolver, not a reuse of the canvas-pixel one.
- Hit-testing lives in a new `board-tools.js` (analog of `canvas-tools.js`'s `hitTopRef`), returning a board ref. The right-click context menu (`context-menu.js`) gains a board-context branch acting on `boardSelection`.
- When editing *inside* a card (after `switchTo`), `canvasSelection` drives scene objects, exactly as today. Two contexts, two runtime stores, both non-undoable. `syncLegacy()` is unaffected.

### 3.4 Undo and persistence

- **Undo:** `state.board` and `state.boardSelection` are **not** added to `history.snapshot()`. Board spatial edits (drag, resize, arrange, group) are document operations, exactly like `addPage`/`deletePage`/`movePage`, which today never call `saveStateToHistory`. Scene edits *inside* a card remain fully undoable (they are normal `state` edits once `switchTo` loads the page). **Board-ops undo is a deferred follow-up**, not a v1 gap. Because `restore()` uses `Object.assign(state, snap)` over snapshotted keys only, board layout survives undo of scene edits (desirable: undoing a crop should not wipe your arrangement).
- **Persistence:** the board travels with the **document**, sibling to `pages`/`active`. `serializeDocument()` adds a `board` key (objects only; `camera` is runtime and stripped). `applyDocument()` restores it. Bump **`DOC_VERSION` 13 to 14** in `pages.js`. `SCHEMA_VERSION` stays 19 (the per-design payload shape is unchanged; a page still carries a full `serializeFull` envelope).
- **Migration `migrateBoardV14(doc)`:** a pre-v32 document has no `board`. Wrap it: if `pages.length === 1` and there is no image, emit a single centered card; if `pages.length === 1` with an image, one centered card ref'ing that page; if multiple pages, lay their cards out in a default grid (e.g. a few columns) ref'ing each `pages[i].id`. Overlays (text/arrow/group) start empty. Camera reset to `{0,0,1}`.

### 3.5 State registry (to be added to CLAUDE.md on ship)

| Key | In `snapshot()` (undo) | Serialized | Notes |
|---|---|---|---|
| `board` | no (deliberate; document op, mirrors `pages`/`active`) | document layer (`serializeDocument`), `DOC_VERSION` 13 to 14 | `camera` is runtime-only and stripped; a `card` object refs a `pages[i].id`; scene payload still lives in `pages[i].payload` and persists unchanged |
| `boardSelection` | no (deliberate) | no | runtime-only, parallel to `canvasSelection` |

## 4. Pillar: Seed (URL to set)

### 4.1 v1 (ships): page-URL to image-cards

Paste a page URL. A new serverless function `api/scrape-page.js` fetches the page HTML server-side (reusing the SSRF/private-IP guards already in `api/fetch-url.js`), extracts the page `title` plus discovered images (Open Graph `og:image`, `<link rel="apple-touch-icon">`, hero `<img>`/`<picture>` sources, favicon), and returns a small JSON manifest `{ title, images: [{url, w, h, alt}] }`. The client then drops these as board `card` objects in a tidy default arrangement, fetching each image CORS-clean through the **existing** `/api/fetch-url` media proxy (which already streams image bytes with permissive CORS) and loading each as a page via the normal `loadImage()` entry point. Brand Brain, if a brand is set/enforced, is applied to the new pages.

This reuses the upload/drop/paste path (`ext-receiver.js` feeds the same `loadImage()`), the CORS proxy, and the pages engine. The new server code is a small HTML scraper, not a headless browser.

### 4.2 v1.1 (deferred): live-page screenshots at breakpoints

True "screenshots of the live page at mobile/tablet/desktop" needs a headless-browser function `api/screenshot.js` using `@sparticuz/chromium` (Vercel-compatible, no system Chromium). This is real new backend infra: a large dependency, cold-start cost, and per-request compute. It is a separate, opt-in tier, explicitly deferred from v32.0. The v1 image-card flow is enough to deliver the "paste a link, get a set" magic moment and to validate the board; full rasterization can land as v32.1 without touching the board architecture.

## 5. Pillar: Control (conversational studio)

The existing Design Agent (`src/features/ai-agent.js`, nine tools, streaming, memory) is promoted from a side panel to a **primary interface**. Cmd-K (`palette.js`) evolves into a streaming chat surface that can issue board-level intent.

New **board-aware agent tools** (added to the agent's tool registry, reusing existing primitives):

- `add_page_from_url({url})` — runs the Seed flow and returns the ids of the new cards.
- `add_page({duplicate})` — wraps `pages.addPage()`.
- `arrange_cards({layout:'grid|row|hero+features|bento', ids?})` — mutates `state.board.objects` positions; a few taste-curated layouts (grid, hero-plus-three, asymmetric bento).
- `group_cards({ids, label?})` / `ungroup({id})` — board group ops.
- `style_cards({ids, aesthetic})` — applies a Brand Brain / `applySpec` look to the selected pages (thin wrapper over the existing `applyBrand`/`applySpec`).
- `export_board({region?|all, format})` — runs board export.

Each tool mutates `state.board`/pages through the same functions a human would, so behavior is identical whether driven by chat or by mouse. The agent's tool-calling, streaming, and memory infra is reused unchanged. Full Producer-style open-ended autonomy remains deferred (per v30 backlog); v32 ships a *scoped, board-oriented* copilot, not an autopilot.

## 6. Pillar: Space (the board surface) — where the new code lives

This is the genuinely new, self-contained work. A new `src/features/board.js` (plus `board-tools.js`) owns:

- **Camera**: pan (drag empty space), zoom (wheel + pinch via existing `gesture.js`), fit-to-content, reset. Camera is runtime-only.
- **Object model**: create/move/resize/rotate/raise/lower/delete for `card`/`text`/`arrow`/`group`. `card` objects are created from `addPage` and ref the page by id.
- **Interaction**: single-click select, shift-click multi-select, marquee rubber-band, drag-move, handle-resize, drag-from-filmstrip-to-board (drop adds a card at the drop point), connect-mode for arrows.
- **Connectors**: an SVG overlay; arrows snap to card edges; `from`/`to` store object ids.
- **Snapping**: reuse `snapping.js` principles for board-space guides (align edges/centers to neighbors and to other cards).
- **Groups**: visual bounding + group-move; `children` store ids.
- **Chrome**: selection boxes, resize handles, hover affordance, drop targets. Drawn in the DOM layer, not in `renderInto`.

It does **not** touch `renderInto`, the four composition paths, `selection.js` (scene), `history`'s per-design snapshot, or `serialize.js`'s `SCHEMA_VERSION`. The only `render.js` change is the one `state.mode === 'board'` branch.

## 7. Taste-skill application (design-taste-frontend)

**Design read:** *Reading the v32 marketing page as a developer/designer-tool launch page for a paradigm-shift release, with a dark-tech / Linear-style language, leaning toward native CSS plus the existing cobalt `#4f7cff` plus Geist, restrained motion.*

Scope is enforced honestly (the skill's own Section 13 excludes dense product UI):

- **Marketing page** (`/open-canvas/`, a new Vite input): full taste-skill machinery. Hero fit, no em-dashes, one accent, shape/color/theme locks, real images (the hero shows one screenshot re-skinned and arranged several ways), motion motivated and reduced-motion honored. Dials: VARIANCE 7, MOTION 6, DENSITY 4.
- **Exported board aesthetics**: any "arrange" or "aesthetic" the agent applies to *exported* cards is taste-curated.
- **Changelog page** (`changelog/index.html`): a taste-skill deliverable. Per the project convention (v16 used glassmorphism), each version's changelog gets a **unique** treatment, never a repeat. v32 must pick a *different* direction from v16's glass, chosen at build time, with the same pre-flight discipline as the marketing page (no em-dashes, one accent, shape/color/theme locks, real imagery, reduced-motion honored).
- **The dense editor/board UI itself**: product-IA principles (clear single-purpose units, consistent selection, predictable affordances), not the marketing-page pre-flight checklist. The parked "Calm Pro" editor restyle is **not** assumed by this spec; it remains a separate, optional effort.

## 8. Non-goals (scope locks)

- No live multi-scene pixel compositor (cards are independent; cross-scene overlays are board-layer only).
- No flat single-coordinate-space canvas rewrite.
- No change to `renderInto` or the four composition paths.
- No change to the per-page editor.
- No board-ops undo in v1 (deferred; matches existing page-op behavior).
- No headless live-page screenshots in v1 (deferred to v1.1).
- No open-ended Producer autonomy (v32 ships a scoped board copilot).
- No tour/storyboard/scroll-story export (separate backlog items).

## 9. Risks and mitigations

1. **Board surface is the largest new module.** It is self-contained and does not fight existing engines, but it is real UI work (camera, hit-testing, drag/resize, connectors, snapping). *Mitigation:* build the board first and dogfood it before wiring Seed/Control; the board is independently useful over the existing pages filmstrip.
2. **Document-level undo gap.** Users may expect undo on card drags. *Mitigation:* keep scene edits fully undoable (the common case inside a card), document the v1 behavior, and treat board-ops undo as a fast follow.
3. **Seed fidelity.** Scraped OG/hero images may not represent the page well. *Mitigation:* v1 is honest about being image-card discovery, not full screenshots; the v1.1 headless tier is the upgrade path. Surface this clearly in the UI.
4. **Thumb freshness at scale.** Many cards each refreshing thumbs could cost. *Mitigation:* reuse the existing debounced `onHistoryChange` thumb refresh (600ms) and only refresh visible/throttled cards; cap active thumb regeneration.

## 10. Build order (one v32, internal sequencing)

1. Board foundation: `state.board`, `board.js`, `board-tools.js`, the `state.mode === 'board'` branch, selection, camera, export composite. Dogfood over existing pages.
2. Persistence: `serializeDocument`/`applyDocument` board key, `DOC_VERSION` 13 to 14, `migrateBoardV14`.
3. Seed v1: `api/scrape-page.js`, client drop-and-arrange, Brand Brain apply.
4. Control: board-aware agent tools, Cmd-K chat surface.
5. Taste-skill marketing page `/open-canvas/` and changelog page (unique treatment, distinct from v16's glass), plus the What's-New toast and version bump to 32.0.0.
6. CLAUDE.md update (State registry, Shipped-features v32 row, an Open Canvas architecture note, checklist if needed).
7. Verify in `npm run dev` (no tests/linter exist).

## 11. Verification

Per CLAUDE.md there is no test runner or linter. Verify by running `npm run dev` and exercising, in-browser:

- Switch to board mode; create/arrange/resize/group/delete cards; pan/zoom.
- Double-click a card, edit the scene, return; confirm thumb refresh and undo of scene edits.
- Save/reload a project; confirm board layout and cards restore (DOC_VERSION migration).
- Paste a URL; confirm image-cards drop and arrange; confirm Brand Brain apply.
- Issue a board intent via chat; confirm the agent tools mutate the board identically to manual edits.
- Export the board (PNG / region); confirm composite matches the visible arrangement.
- Marketing page pre-flight per Section 7.
